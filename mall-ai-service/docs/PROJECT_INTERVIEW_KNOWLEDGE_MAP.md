# 项目面试知识地图

> 版本：2026-08-05
>
> 这不是具体面试题库，也不是简历文案。它记录本项目需要真正掌握的知识
> 领域、代码边界、验证证据和取舍方向。项目完成后，再依据这张地图逐主题
> 进行模拟面试。

## 使用规则

1. 只有“代码已实现、测试已通过、本人能解释”才进入已掌握；仅写在计划里的
   内容标为待学习。
2. 每个主题至少要能完成四件事：画出请求路径、指出关键代码、解释一个失败
   分支、说明测试证明了什么以及没有证明什么。
3. 面试回答优先使用项目真实证据：代码路径、测试数量、现场演示和已知限制。
   不使用未经测量的“生产级”“准确率 100%”等表述。
4. AI 可以生成样板代码、测试骨架和文档初稿；架构边界、授权规则、评测标准
   和失败处理必须由本人做出并能复述。

## 一、产品与系统架构

### 需要掌握

- 产品闭环：认证用户提问 → 语义理解 → 真实订单/物流查询 → 政策证据 →
  售后方案 → 用户确认 → Java 写入或人工转接。
- FastAPI、Java mall、Vue、Redis、Chroma、外部模型之间的职责和请求边界。
- 为什么“一个运行时 Agent + 一个确定性售后状态机”比多 Agent 协作更适合当前
  业务。
- 公共响应 DTO 与内部编排结果的区别：客户看到什么，开发者诊断信息放在哪里。

### 代码与证据

- `app/routers/`、`app/services/`、`app/schemas/` 的分层路径。
- Vue → FastAPI → Java → Redis/模型的时序图。
- 本地真实联调记录、Vue 端到端演示和 Docker 启动记录（交付模块完成后补齐）。

### 状态

- 后端职责边界：已实现并有单测/部分真实联调证据。
- 浏览器录屏、可重复部署：待完成。

## 二、LLM 应用基础与结构化输出

### 需要掌握

- system/user/assistant/tool 消息角色、上下文窗口、Token、temperature 的作用。
- 普通文本生成、原生 Function Calling、严格 JSON 输出的差别。
- Tool Schema 如何描述工具名称、用途、参数类型和 required 字段；模型“看懂”
  schema 不等于服务端授权执行。
- Pydantic 如何把模型返回值转成可校验的内部对象，额外字段、缺失字段和错误类型
  如何处理。

### 面试取舍

- 为什么对业务事实、订单归属和写操作不信任模型；为什么仍然让模型负责语义
  理解、计划和自然语言表达。
- Prompt 是行为约束，不是安全边界；真正边界由代码校验、白名单和 Java 权限
  决定。

### 状态

- 已实现：DeepSeek 解耦、结构化意图、Function Calling、Pydantic 校验。
- 待加强：不同模型 JSON/工具调用兼容性和成本、延迟测量。

## 三、Agent 与工作流

### 需要掌握

- ReAct：Think/Act/Observe 的循环如何由 `while` 实现，模型如何根据观察结果
  决定下一步工具。
- 一次请求内部多步 Agent 循环，与跨请求的 Redis 会话续办是两种不同的循环。
- 工具注册、只读白名单、参数校验、重复调用检测、最大步数、超时、工具失败和
  模型不可用分支。
- 什么时候用 Agent：路径不固定、需要多工具诊断；什么时候用固定流程：退货
  字段收集、确认、写入、权限和幂等。
- LangGraph 的适用条件：显式分支、暂停恢复、人工确认、重试/回滚和长期状态；
  当前不为引入框架而重写 custom ReAct。

### 状态

- custom ReAct 与离线 Agent 评测：已实现并有 6 个合成案例基线。
- 多工具诊断 Agent、LangGraph 迁移：待真实交付闭环后按指标决定。

## 四、RAG 检索、证据和答案边界

### 需要掌握

- Markdown 政策整理、标题切分、chunk 元数据、Embedding、Chroma 持久化、余弦
  距离和 Top-K。
- Recall@K 与“有证据/无证据拒答率”的区别；为什么单一距离阈值不能解决语义
  限定条件。
- Build 11 的二阶段链路：向量候选 → 距离门槛 → DeepSeek 证据充分性 JSON →
  服务端校验 `chunk_id` → 最终模型基于核验块生成回答。
- `candidate_chunks`（可能相关）和 `evidence_chunks`（获准支撑回答）的区别。
- `no_evidence`、`retrieval_unavailable`、`evidence_verification_unavailable`、
  `answer_generation_unavailable` 四种状态，以及为什么都不能悄悄降级成猜测。
- 何时考虑 Hybrid Retrieval、Rerank、ES dense_vector：必须先有排序/召回缺口和
  A/B 指标，不能只为简历关键词添加。

### 当前证据

- 15 个演示政策章节、36 条检索评测、15 条答案忠实性合同。
- 最新真实结果：核验评测有依据 `28/28`、无依据 `8/8`；硬合同 `15/15`，
  2 条措辞差异保留人工复核。

## 五、会话状态与记忆

### 需要掌握

- 浏览器 `session_id` 是会话标识，不是大模型 Token，也不是身份凭证。
- 服务端用 Java 验证得到的 member scope 与 session_id 共同生成 Redis key，
  防止不同账号共享同一对话。
- recent messages、summary、facts、pending tool call、return draft、return
  proposal 分开保存；上下文压缩只能压缩聊天历史，不能丢订单号等结构化事实。
- TTL、草稿过期、一次性确认、重复提交和 Token 刷新后的同成员续办。

### 状态

- Redis-ready 状态存储和上下文压缩：已实现并有单测。
- 多实例部署、故障恢复和容量/延迟指标：交付模块及后续可观测性补齐。

## 六、安全、授权与可靠性

### 需要掌握

- Bearer Token 的签发方、转发路径和 Java 最终授权；它不是 LLM 消耗的 Token。
- FastAPI 不自行判断订单归属，Java 根据当前用户校验订单；模型或前端伪造订单号
  也不能越权。
- Prompt Injection、模型幻觉、伪造来源 ID、敏感字段泄露、超时、重试和网络
  “请求是否已写入”的不确定性。
- 为什么写操作需要服务端确定性规则、显式确认和幂等保护；只读工具与写工具的
  白名单不同。
- 失败时保留可恢复草稿，但阻断售后方案生成或 Java 写入。

## 七、评测、Trace 与自我改进

### 需要掌握

- 单元测试、离线流程评测、真实模型评测、浏览器验收的边界。
- 过程指标：工具顺序、步数、重复调用、停止原因、trace；结果指标：事实来源、
  权限、最终状态、无证据拒答、端到端完成率。
- Trace 只保存脱敏元数据，不保存 Token、完整用户原文或敏感订单信息。
- 失败闭环：脱敏 trace/合成案例 → 人工确认失败模式 → 新评测案例/断言 → 修复
  → 回归测试。AI 可以提出建议，不能自动改生产代码。
- Recall、Precision、拒答率、Grounding 合同、延迟和成本如何一起解释。

## 八、工程交付与部署

### 需要掌握

- `.env` 配置、健康检查、启动顺序、Docker Compose 网络、Redis 持久化和日志。
- Vue 登录态、公共 DTO、错误/加载/待确认 UI；FastAPI 与 Java 的超时和错误映射。
- 本地端到端演示证据：登录 → 查物流 → 多商品退货 → 政策来源 → 确认 → Java
  售后单 → 重复提交/越权被拒。
- README 如何写启动前提、测试命令、模型依赖、已知限制和可复现实验日期。

### 状态

- Docker Compose、浏览器录屏、交付文档：下一大构建模块。

## 模拟面试顺序

1. 先从产品闭环和架构图开始，确认能讲清每个服务的职责。
2. 再按“LLM/Agent → RAG → 状态 → 安全 → 评测”逐主题追问代码和失败分支。
3. 每个主题都要求给出一个真实测试数字和一个已知限制。
4. 最后进行 20 分钟端到端项目答辩，再分别练互联网叙事和制造业叙事。
