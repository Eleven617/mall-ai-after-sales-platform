# Build 13：语义信息收集与可恢复售后草稿

状态：已构建并验证，待本轮代码导读。  
日期：2026-08-07

## 要解决的问题

原有退货草稿能够跨消息保存订单号、商品和原因，但有两个不足：

1. 模型提取出的商品或原因没有“它来自用户哪句话”的可验证依据。
2. 草稿未完成时，用户插入一个无关问题会被当作补充退货信息处理，无法自然切换话题。

## 本次实现

```text
用户原话
  -> DeepSeek 返回候选值 + evidence_span
  -> 服务端检查 evidence_span 确实来自本条原话
  -> 订单号仍由保守订单号解析器决定
  -> Redis 保存 owner-bound PendingReturnDraft
  -> 用户可先问无关问题
  -> 提供订单号 / 已验证商品选项 / 退货原因后恢复草稿
```

- `ReturnFieldCandidate` / `ReturnRequestCandidateExtraction`：把“模型候选”与最终草稿字段分开。
- 商品提示和问题描述只取用户原话中的 `evidence_span`；模型改写的值不会直接写入草稿。
- 原因允许模型做受限归类，例如“耳机坏了”映射为“质量问题”，但该映射仍必须有原话证据。
- 订单号不信任模型：继续使用 `extract_order_sn`，会排除手机号并在多个候选时要求澄清。
- 缺订单号且缺原因时，服务端一次询问两个互不依赖的字段；商品仍要等真实订单商品列表返回后再选。
- 收集草稿阶段的无关消息会交回正常聊天/RAG 路由，草稿保留；待确认写入阶段仍要求明确“确认/取消”，不会因此放宽安全边界。

## 验证证据

- 新增单元测试：模型候选缺少原话证据时拒绝字段、并行追问、无关消息暂停草稿、订单号恢复草稿、入口路由保留草稿。
- 全量 Python 回归：`110/110` 通过。
- 真实 DeepSeek 单条验证：对“订单号是 202607240001，我买的黑色无线耳机坏了，无法充电，想申请退货”，模型返回了订单号、商品、质量问题和描述候选及其原话证据；服务端验证后得到同一组可用草稿字段。
