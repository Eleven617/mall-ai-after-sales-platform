# Build 19 Phase B：AI 质量评测 Agent 与开发者质量页

**状态：** 已构建、单元测试通过、Docker 本机代理链路验收完成（2026-08-20）。
这是 Build 19 的第三个受控 Agent，不是第四个 Agent，也不启动 Build 20 的 Hybrid
Retrieval、Rerank 或其他 RAG 升级。

## 解决的问题

客户诊断 Agent 或运营分析 Agent 被修改后，已经修复过的事实门槛、权限边界或输出合同
可能回退。此前的 `offline_critic.py` 只是一个确定性合同工具，不能形成一个由开发者独立
访问、可重复回放、可审阅的质量角色。

本阶段将它收口为 **AI 质量评测 Agent**：它只回放仓库中版本化、虚构、脱敏的 EvalCase，
先用确定性比较器判断结果，再在明确开启时让模型仅对已失败的合成案例提出归因建议。

## 用户、数据可见性与真实验收路径

| 身份 | 可见内容 | 不可见/不可做 |
| --- | --- | --- |
| 客户 | 原有客户回复、事实卡、售后流程 | 质量套件、运行记录、CaseHandoff、Trace、RAG 内部内容 |
| 运营人员 | 原有脱敏 CaseHandoff 与聚合运营分析 | 质量页面、客户原话、订单号、Token、评测运行记录 |
| AI 质量开发者 | 合成案例的安全预期/实际摘要、合同代码、可选 AI 建议、人工审批状态 | 生产数据库、真实聊天、真实 CaseHandoff、订单号、Token、RAG 原文、生产 Trace |

唯一的本机验收路径：独立开发者身份登录 `/quality` → 手动重跑合成评测 → 浏览器代理调用
`/api/quality/evaluations/run` → 查看 9 条安全投影结果。该路径不读取业务表，也没有
订单、售后、Outbox 或 CaseHandoff 写入。

## 执行链路

```text
开发者独立 Java 管理员身份
  -> FastAPI /quality/me 验证专用角色
  -> 加载版本化 EvalCase JSON
  -> 客户诊断图注入合成只读工具 + 关闭 Trace 记录
     或运营分析注入合成聚合指标
  -> 仅保留安全输出投影
  -> 确定性合同比较器输出 PASSED / FAILED 与违反代码
  -> 仅在确定性失败且开发者显式勾选时调用一次模型归因
  -> 内存中保存本次运行与人工 APPROVED / REJECTED 状态
```

## 固定合成套件与合同

`evals/quality_agent_cases.v1.json` 是仓库版本化套件。首批 9 条案例覆盖：

1. 订单、物流均成功但政策无证据；
2. 订单成功、物流未核验，绝不能得到 `policy_insufficient`；
3. 工具故障安全停止；
4. 非当前账号订单只要求核对标识，不能产生转人工；
5. 纯政策咨询；
6. 含合成订单引用、Token、原话/RAG 内容字段的 CaseHandoff 必须被边界拒绝；
7. 运营草稿只能引用给定聚合数字；
8. 运营草稿声称写入退款/Outbox 必须被拒绝；
9. 运营草稿编造不存在的数字必须被拒绝。

第 6、8、9 条是攻击性合成夹具。它们的内部不安全输入会被确定性边界检测到，
所以“检测到预期拒绝”对测试本身是 `PASSED`；页面只显示违反代码，不显示被注入的值。
真实回归若不再被检测，会变成 `FAILED` 并令 CI 脚本返回非零。

## 权限、成本与回退

- Java 新增独立 `AI质量开发者` 角色；订单管理员、商品管理员、超级管理员和客户均不继承
  此权限。FastAPI 每次质量接口请求均回调 Java `/ai/developer/me` 验证。
- 普通重跑完全离线，不调用 DeepSeek。开发者勾选“失败时请求 AI 归因建议”后，只有已被
  确定性比较器判为违反合同的合成案例才会额外调用模型。
- 模型不可用、超时或结构化输出不合格时，确定性通过/失败不改变，只有 `failure_analysis`
  留空；模型建议永远带 `requiresHumanApproval=true`，不能自动改代码、Prompt、政策、权限、
  测试或业务数据。
- 评测运行记录是进程内内存，不是业务记录；服务重启后清空，绝不影响 Redis 会话、MySQL
  订单、售后、Outbox 或真实 CaseHandoff。

## 重点代码

1. `app/services/quality_evaluation_agent.py`：隔离回放真实客户诊断/运营分析核心，生成安全投影，
   决定性比较先于模型归因。
2. `app/routers/quality.py` 与 `app/services/quality_developer_client.py`：开发者独立 Java 角色边界，
   不复用客户或运营 Token。
3. `mall-ai-web/src/QualityPanel.vue`：只渲染评测结果与人工审批，不渲染输入、业务实体或内部原始数据。

## 明确非目标与边界

- 不代表真实模型对所有用户输入的准确率，也不取代 Build 17 的质量检查点。
- 不读取生产数据，不做生产 Trace 评审，不提供自动修复、自动发布或业务写入。
- 不持久化审批历史，不做多开发者协作、告警平台或线上监控；这些需要独立需求对齐。
- 不把评测套件附加到客户或运营的每个请求；它只在开发者手动运行或 CI 中运行。

## 后续学习重点

学习时应按“链路 → 三个重点代码文件 → 合同失败案例 → CI/非目标”的顺序，重点能讲清：

- 为什么确定性比较器必须在 LLM 归因之前；
- 为什么合成 EvalCase、生产 Trace 和客户原话要严格分开；
- 为什么“预期拒绝的攻击夹具”测试通过，业务合同本身仍被拒绝；
- 为什么此处复用同一 DeepSeek 也可以称为受控 Multi-Agent，而不需要假装三个模型；
- CI 阻止的是未预期回归，而不是已被安全检测到的攻击夹具。
