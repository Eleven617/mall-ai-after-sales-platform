## 使用规则

1. 学习阶段冻结功能代码；发现 Bug、安全问题或验收不符合预期时，可走
   “复现 → 最小修复 → 新增回归测试 → 全量测试”的 Bugfix 流程。
2. 新功能、性能优化、Agent 想法先记录在本文件，不在学习中途插入实现。
3. 每个条目必须标注：问题、价值、实现边界、验收指标、优先级和状态。
4. 不把“写了规划、写了单测、运行了 mock”写成“已真实部署/已上线/模型准确率高”。

## 当前项目定位

旗舰场景不是普通聊天机器人，而是：

```text
自然语言售后申请
  → 语义理解与信息收集
  → 当前登录用户的真实订单校验
  → RAG 政策证据
  → 待确认方案
  → Java 服务二次校验后写入售后单
```

V1 已完成的是“可控业务骨架”：结构化状态、RAG 证据、Java 安全契约、
一次性确认、只读 Agent 边界、回归测试。它是之后 AI 能力的底座，不是最终
展示形态。

## 不做四个在线 Agent：一个运行时 Agent + 一个离线评测角色

初期不做多 Agent 协作系统。那会增加状态同步、调试和评测难度，却未必增加
业务价值。

| 角色 | 运行方式 | 负责内容 | 不能负责的内容 |
|---|---|---|---|
| 客服编排 Agent | 用户请求时在线运行 | 语义提取、追问规划、多工具诊断、基于证据生成回复 | JWT 授权、订单归属、内部 ID 决定、直接写售后单 |
| 售后工作流 | 服务端确定性状态机 | 草稿、字段依赖、确认、过期、一次性提交 | 自由推理、绕过审批 |
| Critic / 评测角色 | 离线或测试环境运行 | 根据脱敏 trace 和合成案例提出测试/修复建议 | 修改生产代码、规则、知识库或真实数据 |

“四块能力”指的是一个客服编排 Agent 的能力模块，并不是四个 Agent 同时聊天：

1. 语义提取；
2. 追问规划；
3. 多工具诊断；
4. 评测与改进建议（这一块通常离线运行）。

## 总路线：学习、交付、升级三条线合并

| 阶段 | 目标 | 状态 | 交付证据 |
|---|---|---|---|
| A. V1 基础学习 | 会话状态、RAG、售后工作流、Agent 边界 | 进行中：当前在“售后工作流” | 能读懂代码、解释分支、跑懂单测 |
| B. V1 实际交付 | Vue 接入、Java/MySQL/Redis/FastAPI/RAG 联调、Docker Compose、演示 | 进行中：核心后端真实联调已通过；Docker/浏览器录屏未完成 | 本地端到端演示、录屏、真实验收记录 |
| C. V2 智能升级 | 语义提取、追问规划、多工具诊断、评测 Agent | 未开始 | 对比评测与可解释案例 |
| D. V2 检索升级 | 先测量，再做混合检索/Rerank | 未开始 | Recall@K、无证据拒答、人工案例复核 |

## V1 → V2 的 AI 能力升级清单

### C1. 语义提取升级：从正则优先到“LLM 候选 + 服务端证据校验”

**当前局限**

- 纯数字订单号的正则对倒装句有一定覆盖，但对口语、省略、尾号、非纯数字编号
  和多个不同类型号码的语义区分有限。
- 当前 LLM 的商品提示可能缺少“它来自用户原话哪里”的可验证依据。

**目标设计**

```json
{
  "order_candidates": [
    {
      "value": "202607240001",
      "evidence_span": "我想退掉 202607240001 这笔订单",
      "semantic_type": "order_number"
    }
  ],
  "product_mentions": ["黑色耳机"],
  "reason": "质量问题"
}
```

**服务端仍需做的事**

- 候选值和证据片段必须能回指原始用户消息；
- 手机号、物流号、订单号等类型不能仅凭模型自报直接相信；
- Java 必须验证候选订单属于当前登录用户；
- 多个有效候选时不猜测，向用户澄清；
- 商品提示必须能唯一匹配真实订单商品，否则展示候选让用户确认。

**验收指标**

- 订单候选提取 Precision / Recall；
- 错误订单进入写操作的次数必须为 0；
- 澄清率、平均完成轮数；
- 倒装、口语、手机号+物流号+订单号混合等评测集覆盖。

**优先级**：P1，完成 V1 实际联调后实施。

### C2. 追问规划：一次收集能同时收集的独立信息

**当前局限**：缺订单号时，V1 先追问订单号；体验上还可同时邀请用户补充退货原因。

**目标设计**：服务端先计算字段依赖，再让 LLM 只负责措辞。

```text
order_sn：必须先获得，才能查询真实商品候选
reason：可与 order_sn 同时询问
product：依赖真实订单商品列表，不能在查单前凭空让用户选内部对象
```

LLM 的输入是“允许询问的字段、已有事实、不能编造的规则”，输出自然语言问题；
后端仍决定允许问哪些字段。

**验收指标**：不要求用户提供内部 ID；不会问已知字段；可减少无必要轮数。

**优先级**：P1，和 C1 合并为同一个“智能信息收集”构建批。

### C3. 多工具诊断 Agent：发挥 Agent 的真实价值

适用场景是路径不固定的问题，而不是固定的退货写流程。例如：

> “订单为什么一直没到，我现在应该怎么办？”

运行时 Agent 的可选动作受白名单限制：

```text
查订单 → 查物流 → 检索政策 → 形成带证据解释 / 人工转接摘要
```

它可以规划多个只读工具调用、根据观察结果继续或停止；退货写入仍回到受控工作流。

**验收指标**：工具调用轨迹可追踪、重复调用受限、错误不编造、引用真实政策来源。

**优先级**：P1，C1/C2 完成后。

### C4. Critic / 自审评测角色：可控的“自我提升”

它不是让 AI 自动改生产代码，而是：

```text
脱敏 trace + 合成失败对话 + 现有回归结果
  → 发现失败模式
  → 提议新的评测案例、测试断言或修复方案
  → 人工审核
  → 进入 pytest 回归
```

**验收指标**：建议可复现、无真实令牌/订单/用户隐私泄露、每次接受改动都关联测试。

**优先级**：P2，先有稳定的 V1/V2 测试与部署后实施。

## RAG 升级路线：先测量，再增加复杂度

| 顺序 | 内容 | 实施条件 |
|---|---|---|
| R1 | 现有 Markdown 切分、向量召回、来源、阈值拒答、Recall@K | 已有代码；需要真实知识库测量 |
| R2 | 建立售后政策黄金评测集：同义问法、边界问题、无答案问题 | V1 联调时完成 |
| R3 | 关键词 + 向量混合检索 | 当前仅实现“向量不可用时的本地关键词证据降级”；R2 测量后再做真实融合排序 |
| R4 | Rerank 重排序 | R3 仍出现 Top-K 相关但排序不佳时 |
| R5 | Elasticsearch dense_vector / 商品语义检索 | 商品规模、搜索需求或运营场景确实需要时 |

不为了简历关键词而直接写“混合检索、Rerank、ES 向量检索”；必须有前后评测结果。

## LangChain / LangGraph 的位置

- **LangChain**：了解组件抽象和生态即可；当前不迁移，避免为了框架重写已经
  可测的服务边界。
- **LangGraph**：当 Agent 出现多分支、暂停恢复、人工确认、重试/回滚、长期状态
  需要可视化时引入。最合适的首个候选是 C3 多工具诊断 Agent，而不是把固定
  退货写流程强行改成 Agent。
- **当前 custom ReAct**：保留并学习，因为它能让你解释 Function Calling、工具
  白名单、循环停止条件和观察结果如何进入下一步。

LangGraph 是“让复杂 Agent 图更易维护和可恢复”的工具，不是项目有 Agent 的前提。

## V1 实际交付与部署清单（优先于大规模 V2 功能）

### B1. 前后端与登录态

- Vue 聊天界面展示普通回答、RAG 来源、待补信息、商品选项、待确认方案；
- 从现有 mall 登录态获取 Bearer Token，传给 FastAPI；
- FastAPI 仅转发 Token 给 Java，不自行判断订单归属；
- 使用稳定的公共 `session_id`，但由服务端按 Java 已验证的 `member_id` 做作用域，
  再在 Redis 中保存会话、草稿和待确认方案；不能把客户端编号单独当作身份。

### B2. 本地真实联调

- Java mall + MySQL；
- Redis；
- FastAPI AI 服务；
- Chroma / Embedding / LLM 提供方；
- 仅用可删除的测试账号和测试订单完成 `manual_live` 验收。

### B3. Docker Compose 与演示

- 用 Compose 编排能容器化的本地服务；外部模型 API 使用环境变量；
- 提供启动、初始化知识库、运行验收、停止服务的脚本；
- 录制“多商品退货 → 政策来源 → 确认 → Java 售后单”的演示；
- 记录真实验证日期、模型/Embedding 版本和已知限制。

### B4. 可观测性（后续）

- 结构化、脱敏 trace；
- 失败类型统计、人工转接率、RAG 无证据率、工具失败率；
- 如需展示，可做只读的本地评测/日志页面；不展示用户原文、Token 或订单隐私。

## 暂缓项（避免范围膨胀）

- 通用 Multi-Agent swarm、由 LLM 自主选择角色，或多个共享同一权限/工具集的“伪多 Agent”；
- 独立 MCP Server、通用 Skill Loader 和跨会话长期用户记忆，直到出现真实第二消费者或稳定第二业务能力；
- Kubernetes；
- 私有模型部署；
- Elasticsearch 向量迁移；
- 自动修改生产规则或代码的“自进化”。

RabbitMQ 售后状态事件与角色化 Agent 平台已获批准，但分别受 Build 18 和
Build 19 的准入条件约束，不能提前作为简历关键词或空壳功能实现。

## 2026-08-07：V2 差异化路线决策

### 目标不是“更多工具”，而是“更强的业务闭环”

当前四个只读工具（订单、物流、库存、政策）不是项目竞争力不足的证据。工具数量
本身不是 Agent 指标：过多、粒度过细且没有真实业务目的的工具，会增加模型选择错误、
Token 成本、评测组合数和权限面。

V2 的旗舰能力定为 **订单异常诊断与人工协同 Copilot**：针对“为什么没到、现在该
怎么办、是否需要售后”等路径不固定的问题，形成可追踪的只读诊断和可交接的方案；任何
写操作仍回到现有受控售后工作流。

```text
用户自然语言问题
  -> 已验证订单上下文 / 语义候选
  -> Agent 按需查询订单、物流、政策和后续真实业务工具
  -> 服务端生成事实包与证据包
  -> 模型只生成不越过事实边界的解释与下一步建议
  -> 用户自助继续受控售后，或转人工并携带脱敏诊断摘要
```

### 建议构建顺序

#### Build 13：自然语言信息收集与可暂停售后任务（P1）

- 合并 C1、C2 和 IDEA-004：LLM 提取带原话证据的候选，服务端验证候选；一次询问可并行
  收集订单号与原因；支持暂停售后草稿、处理只读问题、再恢复。
- 不可突破：模型不能把电话号码、物流号或猜测的商品直接提升为订单/内部 ID；Java 和
  真实订单商品仍是唯一确认来源。
- 验收：倒装句、混合号码、多个订单候选、插入物流询问、恢复草稿、跨账号恢复拒绝。

#### Build 14A：客户侧售后状态可追踪（P1，V1 业务闭环补齐）

- 复用原 Java 商城的售后状态语义：待审核、已同意退货、售后完成、已拒绝；新增客户侧
  最小只读查询，不新造快递、仓储、支付或退款领域系统。
- Java 必须基于当前 JWT 对应会员的真实订单过滤售后单；FastAPI 和 Vue 只能接收售后单号、
  订单号、商品、原因、状态、处理说明与时间，不能返回手机号、地址、价格、内部订单 ID
  或审核人员身份。
- 提交成功必须返回售后单号和初始状态；“查看售后记录”是只读能力。状态变更仍属于原后台
  人工操作，AI 不能同意、拒绝或完成退款。
- 验收：两个账号只能看到各自售后记录；创建响应和列表均无敏感字段；Vue 可展示状态卡片；
  Java、FastAPI、Vue 真实联调通过。
- 状态：已验证（2026-08-10 本机 Docker 联调；双账号隔离、字段白名单与状态卡片通过）。
  这不是生产上线；物流退回、仓储收货、退款和通知仍不在本模块范围内。

#### Build 14：证据驱动的订单异常诊断 Agent（P1，V2 旗舰）

- 使用已有订单、物流、RAG 工具实现第一个完整诊断案例，并只在真实 Java API 支持时增加

#### Build 20：RAG 2.0——测量驱动的 Hybrid Retrieval 与 Rerank（P1）

**定位：** 这是项目下一条核心 AI 能力主线，不是为了简历关键词临时增加的可选项。现有
Chroma + 本地 BGE dense retrieval 是对照基线；本 Build 将完成可复现实验，并实现
Hybrid Retrieval 与 Cross-Encoder Rerank 的候选链路。是否默认启用每一层由指标决定，
不是由“技术名词越多越好”决定。

**要解决的问题：** 售后政策问法既有“七天无理由、拆封、激活、运费险”等精确术语，也有
“耳机试过还能退吗”这类口语化表述。单一向量检索可能漏掉术语，单一关键词检索又可能漏掉
语义近义表达；即使正确证据进入 Top-K，也可能没有排到足以被回答模型使用的位置。

**目标链路：**

```text
用户问题
  -> Query normalization / 可评估的查询改写（如评测证明需要）
  -> Dense Retrieval（现有向量召回）与 BM25 Retrieval（关键词召回）并行
  -> Reciprocal Rank Fusion, RRF 融合候选排名
  -> Top-N 候选的 Cross-Encoder Reranker
  -> 现有证据核验门槛
  -> 有依据回答 / 无依据拒答
```

**实施顺序与不可省略的测量门槛：**

1. **Build 20.0：黄金评测集与基线。** 扩充项目自有、人工复核的政策语料与问题集，覆盖同义
   改写、术语精确匹配、近似但错误的政策、旧新规则冲突、无答案问题及恶意/无关检索文本。
   为每题标注允许证据和应拒答的情形；记录 dense baseline 的 Recall@K、MRR/nDCG@K、
   grounded-answer / abstention 正确性、p95 时延与成本。
2. **Build 20.1：Hybrid Retrieval。** 保留 dense baseline，新增 BM25 与 dense 的并行候选
   召回、RRF 融合和可开关实验路径。不能把“向量不可用时的关键词降级”误写成 Hybrid Retrieval。
3. **Build 20.2：Rerank。** 对融合后的 Top-N 使用 Cross-Encoder Reranker，并与仅 Hybrid、
   仅 dense 进行同一评测集比较。Reranker 的输入只包含问题和已允许的政策候选，不能读取订单、
   客户原话、Token、业务 Trace 或内部提示词。
4. **保留决策。** 记录每层在召回、排序、忠实性、拒答、p95 时延和成本上的前后差异。若某层
   没有可复现收益，代码/实验结果保留为学习证据，但不默认放入客户在线路径；若有收益，说明
   默认链路和回退策略。

#### Build 21：可恢复的 Human-in-the-Loop Agent Workflow（P1，新增候选）

**定位：** 将 LangGraph 从“单次请求内的有状态图”升级为可暂停、可恢复的受控执行。它不是把
固定的售后写流程交给模型，也不允许 Agent 在没有人确认时执行退款、订单或售后写入。

**真实场景：** 客户诊断在多订单候选、信息不足或需要客户选择时安全暂停；客户稍后补充信息、
服务短暂中断或 AI 服务重启后，系统可以从同一受限诊断状态恢复，而不是盲目重跑整条路径。

**设计原则：**

```text
LangGraph interrupt()
  -> persistent checkpointer 保存允许持久化的 ResumableState
  -> 客户/人工提交安全的 resume 输入
  -> 使用同一 owner-bound thread_id + Command(resume=...)
  -> 从中断点继续只读诊断
  -> 任何业务写入仍回到 Java 确认、幂等和事务边界
```

- 不直接持久化当前图的完整内存 State：其中可能包含 Bearer Token、原始消息、工具原始结果、
  RAG 内容或模型消息；必须先拆分 `RequestContext` 与 allow-listed `ResumableState`。
- `thread_id` 必须由 Java 已验证身份和会话范围绑定，不能由浏览器任意指定；不同客户、匿名与
  已登录会话之间不得恢复彼此的 checkpoint。
- 选择持久化 Redis 或 MySQL 时同时定义 TTL、删除语义、版本迁移、并发恢复策略、容量上限与
  加密/访问边界；内存 Saver 只可用于测试。
- 任何中断点之前的副作用必须幂等；已有 Java 售后提交幂等、CaseHandoff 去重与 Outbox 事件
  幂等不因引入 Checkpointer 而取消。

**验收标准：**

- 强制在至少两个中断点后重启 AI 服务，正确身份可恢复、错误身份得到拒绝；
- 恢复不重复执行不应重复的工具或业务写入，重复 resume 结果可解释；
- checkpoint 数据与日志均不含 Token、客户原话、完整订单号、RAG 原文或原始工具载荷；
- 已过期、已删除、版本不兼容、并发恢复和取消场景有确定性结果；
- 页面能说明“正在等待什么、恢复后会做什么、不会做什么”。

**关键学习词：** Durable Execution、Checkpointing、Persistent Checkpointer、thread_id、
Interrupt、Command Resume、Human-in-the-Loop、State Sanitization、TTL、Fault Recovery、
Idempotent Side Effects。

**状态：** 已完成需求对齐、代码/单元验证、Docker 匿名恢复和登录双账号网站代理恢复/拒绝验收：Build 21 仅为订单异常诊断的缺标识等待点增加
脱敏、owner-bound 的 LangGraph `interrupt()` / Redis checkpointer / `Command(resume=...)` 恢复；不持久化
完整诊断 State，也不改变统一售后写入。A 在 AI 服务重启后可恢复只读诊断，B 在会话归属校验处被拒绝，
且售后记录未变化；详见 `docs/BUILD_21_DURABLE_HITL_REQUIREMENTS_AND_IMPLEMENTATION.md`。不可为了 Checkpointer
关键词把现有短时只读诊断强行改成长期自治任务。

#### Build 22：统一售后 Agent 最终收口——受控 ReAct、可恢复执行与可靠性闭环（P1）

**定位：** 在既有第三个质量评测 Agent 的基础上，补齐“发现问题 → 脱敏归纳 → 合成回放 → CI

**目标链路：**

```text
allow-listed safe trace metadata
  -> 节点 / 工具 / 时延 / 失败类别 / 合同结果的结构化观测
  -> 人工确认一个真实失败模式
  -> 删除敏感信息并抽象为 Synthetic EvalCase
  -> Trajectory Evaluation + Red-team regression
  -> CI 阻止未预期回归
```

**最小范围：**

- 定义统一、版本化的安全 Trace schema：只允许 flow、node、tool_name、duration、result_kind、
  diagnosis_category、evidence_status、handoff、contract_violation 等字段；禁止 Token、客户原话、
  完整订单号、地址、RAG 原文、原始工具结果和模型 Prompt。
- 对客户诊断、运营分析和质量评测建立 trajectory-level 断言：工具顺序、最大步数、重复调用、
  事实门槛、越权工具、非法 handoff、虚构写入、错误指标引用均可被回放验证。
- 在现有完全离线的 `contract_mock` 套件外，新增受控 `live_model_synthetic` 评测档位：使用
  真实模型、真实 Prompt / Tool Schema / LangGraph 编排，但仅注入版本化合成用户问题、模拟订单
  / 物流 / 政策证据与隔离工具。它评测真实模型的工具选择、结构化输出、拒答、提示注入防御和
  安全轨迹，绝不读取生产聊天、真实订单、真实 CaseHandoff、Token 或业务 Trace，也不产生业务写入。
- `contract_mock` 继续作为每次 PR/CI 的稳定确定性门；`live_model_synthetic` 仅在 Prompt、模型、
  Tool Schema、RAG 或 LangGraph 改动后手动、夜间或发版前运行；重要升级再做受控的
  `sandbox_e2e` 验收。不能让单次非确定性模型调用替代普通单测或成为全部 CI 的唯一裁决。
- Live Eval 固定低温度并记录模型、Prompt、Tool Schema 与评测集版本。权限、敏感字段、写入和
  事实门槛等硬规则仍由确定性比较器裁决；LLM-as-a-Judge 只能在人工校准后辅助评价回答清晰度、
  帮助性等软指标，不能把硬失败改成通过。
- 扩展红队案例：indirect prompt injection、恶意工具结果、跨账号订单探测、敏感字段泄露、模型
  不可用、超时、恢复重放、RAG 无证据和近似政策混淆。

#### IDEA-019：可重复的本地演示场景库（P1，Build 19 学习后的交付基础）

- 用户问题：现有本地演示数据足以验证一条关键安全链路，但运营工作台容易只显示空的聚合卡片，无法连续展示正常订单、政策缺口、跨账号拒绝、售后状态和事件投递等真实分支。

- 计划场景：当前客户的正常订单诊断；政策无证据的人工转接；不存在或其他客户订单的安全纠正；待审核/已同意/已完成/已拒绝售后；按原因汇总；Outbox/投递的成功、处理中和失败状态；订单管理员允许、商品管理员/客户拒绝；Offline Critic 的合成回归案例。
- 不可突破的安全/业务边界：所有数据仅限本机 Compose 数据卷和专用演示账号；不记录明文密码或 Token；不可伪造生产能力；不得为了填满图表而绕过真实业务接口、手工篡改线上式业务状态或让 AI 自动写数据。
- 验收案例与指标：从干净或已知状态一次初始化后，按文档操作可连续完成上述网页分支；每项展示可追溯到真实数据库记录或业务接口；运营分析前后订单、售后和 Outbox 的写入计数符合场景声明；无数据场景保持空状态并明确说明原因。

- 状态：已批准待构建；当前仅完成需求登记，不创建额外测试数据。

#### IDEA-020：按账号隔离的客户历史会话（P1，客户体验与隐私）

- 用户问题：当前“新建会话”会生成新会话并清空页面；Redis 只保留短期多轮上下文，客户无法从网页找回、继续或删除此前的咨询，左侧也只显示不可理解的技术会话 ID。
- 拟议方案：在登录客户的左侧栏提供“新建会话 + 历史会话列表”，按今天/更早分组，展示客户可读的会话标题、最近更新时间和当前选中态；支持打开继续、重命名（可选）与删除。将可展示的会话目录和经审批保留的消息记录持久化，并把 Redis 继续用于短期上下文、草稿恢复和性能缓存，而不是作为客户历史档案。
- 不可突破的安全/业务边界：会话必须以已验证会员身份为唯一归属边界，任何接口和前端缓存均不得跨账号读取；不在标题、列表或日志中泄露订单号、Bearer Token、完整身份证明或内部 trace/RAG/工具结果；需定义数据保留期、用户删除语义、登出/换号后的本地缓存清理和售后业务记录与聊天记录的不同保存规则。
- 验收案例与指标：同一客户新建两段会话后可在左栏分别恢复；客户 A 无法通过猜测 ID 或旧浏览器缓存读取客户 B 的任何会话；删除后列表和服务端可展示历史一致；页面刷新、重新登录和 Redis 上下文过期后，已批准持久化的历史行为符合保留策略；售后申请仍以独立业务记录显示，不依赖聊天记录存在。
- 优先级：P1（Build 19 演示场景库完成后，Build 20 前评审）。
- 状态：已批准待设计；当前不改变 Redis TTL，也不开始持久化客户原始对话。

#### IDEA-021：客户聊天与运营工作台的信息架构重设计（P1，角色清晰与界面体验）

- 用户问题：当前客户聊天页面把“有依据的客服”宣传区、技术性事实卡片和内嵌运营工作台放在同一页面。即使运营身份单独认证，用户仍会同时看到客户账号和运营账号，难以理解自己正在处理什么事项，也不像真实的客户端与内部工作台。

- 验收案例与指标：客户登录后只看到客户界面与自己的历史会话；订单管理员从独立入口登录后只看到运营工作台；运营事项可看懂“为什么进入待办、分析什么数据、不能做什么”，但无法读取客户原话和订单号；商品管理员与客户访问运营路由分别被拒绝；移动端与桌面端均不因侧栏或运营面板遮挡主要任务。
- 优先级：P1（与 IDEA-020 一起完成产品原型和权限路由设计后实施）。

  Build 19.2 的运营页范围，不在此条扩展客户数据或业务写入。

#### IDEA-022：AI 质量评测 Agent 与开发者质量页（P2，Build 19.2 后）

- 明确目标：第三个 Agent 的核心工作是“回放版本化合成测试问题，比较目标 Agent 的实际输出和预期合同，分析失败原因，提出候选回归题/修复方向，等待开发者审批”。它是开发质量角色，不是运营统计 Agent、人工售后 Agent，也不是自动改代码 Agent。
- 要解决的问题：客户诊断或运营分析的 Prompt、工具编排、权限边界被修改后，过去修复的错误可能复发，或新改动引入越权、幻觉、错误转人工和错误事实判断。Critic 负责在 CI 或开发者主动运行时提前发现这些回归。
- 固定评测题合同（版本化 JSON）：每条 `EvalCase` 至少包含 `caseId`、`targetAgent`、虚构的 `syntheticInput`、隔离的 `mockToolResults`/`mockMetrics`、`expectedContract` 和 `schemaVersion`。`syntheticInput` 不是客户原话；模拟工具/指标不访问生产数据库；`expectedContract` 明确允许结果、禁止结果、是否允许 CaseHandoff、是否允许业务写入。
- 执行链路：加载评测题 → 在隔离环境调用目标 Agent（客户诊断首批覆盖订单/物流/政策门槛，运营分析覆盖聚合数字与禁止写入）→ 注入固定模拟工具结果或聚合指标 → 得到实际输出的安全投影 → 确定性比较器先检查合同、权限、分类、证据状态和写入边界 → 失败案例才交给大模型做失败归因、相似失败归并和候选回归题/修复建议 → 开发者审批或驳回。大模型不能跳过确定性比较器。
- Critic 输出合同（结构化 JSON）：至少包含评测运行标识、案例标识、`passed`、实际输出安全投影、违反的合同代码、失败类型、证据摘要、候选测试/修复建议和 `requiresHumanApproval=true`。结果只通过质量接口返回给前端；不要求开发者打开或下载独立 JSON/HTML 报告文件。CI 可保留机器输出作为合并闸门。
- 数据与隐私边界：Critic 不接收每条客户聊天，不接收线上真实 CaseHandoff，不读取生产数据库、Token、RAG 原文或完整 trace。线上 CaseHandoff 只供 Java/运营分析使用；人工确认新失败后，才将其抽象成虚构输入、模拟证据和预期合同。允许传入 Critic 的 trace 只能是 `flow/event/step/tool_name/diagnosis_category/evidence_status/handoff` 等白名单元数据。
- 与其他角色的边界：运营分析 Agent 解释“真实运营聚合数据反映了什么压力和关注方向”；质量评测 Agent 验证“改动后 AI 是否仍满足测试合同”。运营建议不能自动生成评测题；人工/开发者确认失败并脱敏后，才加入评测集。Critic 建议不能直接修改代码、Prompt、政策、权限或业务状态。
- 开发者质量页：使用独立开发者身份和独立 Token；前端直接读取质量接口 JSON，展示评测套件版本、通过/失败总数、失败案例、预期与实际差异、合同代码、模型候选建议及审批状态；不展示客户原话、订单号、Token、RAG 原文、生产 trace；可提供隔离环境“重跑评测”，不提供自动发布或业务写入按钮。
- 失败案例流程：有权限人员从客户反馈、运营现象、受控诊断记录、CI 失败中确认问题 → 删除/抽象敏感内容 → 编写合成 `EvalCase` → 人工确认预期合同 → 进入版本化评测集 → 后续每次改动自动回归。未知问题不能由当前 Critic 凭空发现。
- 验收案例与指标：故意注入订单号、Token、原始消息或越权 trace 时确定性检查失败；订单已核验但物流未核验的门槛案例能阻止错误 `policy_insufficient`；运营分析输出超出给定聚合数字或声称执行写操作时失败；每个已批准失败模式可追溯到一条无敏感信息的版本化评测题；质量页能展示通过/失败、失败原因、候选建议和人工审批状态；客户、商品管理员和运营身份不能访问；不启动客户/运营在线请求，不产生业务写入。
- 优先级：P2（Build 19.2 收口并积累首批评测题后实施；不阻塞客户体验与运营页交付）。
- 状态：已构建、定向单测和 Docker 网页代理验收通过。旧的确定性 `offline_critic` 保留为内部
  合同工具，不再作为第四个角色；第三个 Agent 使用 9 条版本化合成 EvalCase、独立开发者身份、
  安全结果投影、可选失败归因和内存审批状态。默认完全离线，CI 工作流已准备但尚未在远程 GitHub
  根仓库实际执行；详见 `docs/BUILD_19_QUALITY_EVALUATION_AGENT.md`。

### LangGraph 的采用结论

Build 14 已满足明确循环、多终止分支和可审阅执行轨迹等准入条件，因此采用
LangGraph 编排诊断运行。它不替代 Redis 的跨请求会话状态，也不意味着后续每个角色
都要使用 LangGraph。

后续只有在新的角色再次出现多分支、暂停恢复、分级重试或图状态可视化需求时，才复用
LangGraph；不为简历关键词迁移 custom ReAct。

### IDEA-004：可暂停、可恢复的售后会话与话题切换

- 日期：2026-07-29
- 类型：体验优化 / Agent 能力
- 用户问题：用户正在补订单号或商品时，可能临时问“物流到哪了”或普通问题；
  当前 V1 会优先继续售后草稿，除非用户明确说“取消”。
- 为什么当前实现不够：固定工作流保证了写操作安全，但无法自然处理“暂停当前
  任务、完成只读问题、再恢复草稿”的多意图会话。
- 拟议方案：保留授权绑定的售后草稿，引入受限会话路由状态：继续售后 / 取消售后 /
  暂停售后并处理只读新意图 / 恢复售后。暂停不能自动提交、不能丢失草稿、不能让
  新话题继承错误业务参数。
- 不可突破的安全/业务边界：只有明确确认才能写入；切换话题不得清除或篡改已有
  草稿；不同登录用户不得恢复他人的草稿。
- 验收案例与指标：多轮中插入物流查询、普通聊天、取消、恢复；每种路径的草稿、
  Token 绑定和写接口调用次数均可验证。

- 状态：已批准待构建。

### IDEA-005：售后提交幂等键与超时后的安全重试

- 日期：2026-07-29
- 类型：可靠性 / Java 集成
- 用户问题：FastAPI 调用 Java 写接口超时后，可能无法判断 Java 是未收到请求，还是
  已经写入但响应丢失；当前 V1 为防重复而消费 proposal，并要求用户到售后列表核实。
- 为什么当前实现不够：安全优先但重试体验较差，用户可能需要手动核对后重新发起。
- 拟议方案：将 `proposal_id` 作为不可预测的幂等键传入 Java；Java 为该键建立唯一约束
  或持久化记录。相同键的重复请求返回第一次创建结果，而非创建第二张售后单。FastAPI
  可把超时状态标为“提交结果未知”，随后查询 Java 售后状态。
- 不可突破的安全/业务边界：幂等键不能替代 JWT、订单归属、订单项归属和订单状态校验；
  写入仍需用户确认。
- 验收案例与指标：模拟“Java 已写入但响应超时”与“Java 未收到请求”两类情况；重复
  确认最多产生一张售后单，最终用户可得到明确状态。
- 优先级：P1（V1 真实联调后）。
- 状态：已在 Build 16 实现，并在本机 Docker 完成真实客户链与 Java 同键复放/篡改拒绝复验；
  仍不宣称远程生产部署或完整故障注入演练。
