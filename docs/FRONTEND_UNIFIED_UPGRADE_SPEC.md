# Mall 前端统一展示级升级需求说明

> 文档目的：一次性完成 Mall AI 售后平台的前端统一升级，让客户页、开放任务 Agent 工作台、运营工作台、人工协同处理台和质量评测台形成一套完整、统一、可演示的产品体验。
>
> 本文是前端实现对接文档。实现完成后应作为一个完整的前端升级提交，不拆成“先改颜色、以后再补功能”的多轮半成品。

## 1. 本次升级要解决的问题

当前前端已经具备客户售后咨询、开放任务、人工协同、运营分析和质量评测能力，但页面仍然更像多个功能页面的集合。访客打开 GitHub README 截图时，需要在很短时间内看懂三件事：

1. 这是一个面向电商售后的 AI Agent 产品，而不是普通聊天机器人；
2. Agent 会围绕用户目标调查订单、物流、库存和政策事实，并生成可确认的行动方案；
3. 系统有运营协同和质量评测闭环，而不是只展示一段模型回复。

本次升级的目标是“产品展示级”，不是单纯装饰页面：

- 10 秒内看懂产品定位；
- 30 秒内看懂 Agent 如何从目标走到方案；
- 1 分钟内看懂事实、证据、人工确认和评测结果之间的关系；
- 保留现有后端接口、权限边界、测试契约和真实业务逻辑；
- 让 README 中的 3 张截图和 1 个短 GIF 足以代表整个项目。

## 2. 现有前端范围与不可破坏内容

### 2.1 页面和组件

需要统一升级以下页面和组件：

- `mall-ai-web/src/App.vue`：客户售后咨询、历史会话、事实卡、政策卡、售后方案、人工协同记录；
- `mall-ai-web/src/AgentTaskWorkspace.vue`：开放目标、任务计划、任务产物、待确认行动、补充信息和继续任务；
- `mall-ai-web/src/OperationsPage.vue` / `OperationsPanel.vue`：运营概览、转人工统计、最小化事项和分析草稿；
- `mall-ai-web/src/ServiceOperationsPage.vue` / `ServiceOperationsPanel.vue`：人工案件领取、补件、核验、处理和结案；
- `mall-ai-web/src/QualityPage.vue` / `QualityPanel.vue`：版本化评测、运行结果、单 Case、失败归因建议、回放和反馈候选；
- `mall-ai-web/src/style.css`：全局视觉变量、公共控件、页面外壳、响应式和可访问性样式；
- `mall-ai-web/src/types.ts`：原则上不改现有业务类型，仅在确有必要时增加前端展示所需的可选字段。

### 2.2 必须保持不变的接口和行为

- 不改变登录、会话、Agent 任务、售后申请、运营分析、人工案件和质量评测的接口路径及请求语义；
- 不改变 Java 最终写入、人工确认、权限隔离、Outbox、评测回放等后端行为；
- 不把前端显示字段当作新的业务事实；
- 不在前端暴露 Token、原始 Prompt、内部工具参数、客户隐私或模型内部思考内容；
- 不新增重量级 UI 框架、图表库或运行时依赖。优先使用 Vue 现有能力和 CSS；
- 所有现有空状态、加载状态、错误状态和禁用状态必须继续可用，并在视觉上统一。

## 3. 统一产品定位和视觉方向

### 3.1 产品名称和一句话说明

页面统一使用：

- 产品名：`Mall AI 售后平台`；
- 客户侧副标题：`可信电商售后 Agent`；
- 内部侧副标题：`事实、证据与人工协同的售后工作台`。

不要在首屏堆叠 `Agent Runtime`、`Context Pack`、`RunManifest` 等内部实现名词。技术名词可以在详情区域出现，但首屏先让用户理解业务价值。

### 3.2 视觉气质

目标气质：可信、清晰、克制、现代、偏 B2B AI 产品，而不是营销网站或纯聊天软件。

- 页面背景：浅灰蓝，不使用纯白铺满整个浏览器；
- 内容容器：白色、轻边框、柔和阴影、较大圆角；
- 主色：深蓝或蓝紫，用于主操作和 Agent 状态；
- 辅助色：青绿色，用于已确认、已完成和可用状态；
- 警告色：琥珀色，用于待确认、证据不足、需要补件；
- 错误色：红色，仅用于失败、不可用和危险操作；
- 紫色：只用于 Agent 任务或计划状态，避免和成功、警告混淆；
- 所有颜色必须同时有文字标签，不能只靠颜色表达状态。

### 3.3 建议的全局设计变量

在 `style.css` 的 `:root` 中集中定义变量，所有页面复用，不再各自写一套相近颜色：

```css
:root {
  --ink-950: #0f172a;
  --ink-800: #1e293b;
  --ink-600: #475569;
  --ink-400: #94a3b8;
  --line: #e2e8f0;
  --surface: #ffffff;
  --surface-soft: #f8fafc;
  --page: #eef3f8;
  --brand: #2563eb;
  --brand-deep: #1d4ed8;
  --agent: #7c3aed;
  --success: #0f766e;
  --warning: #b45309;
  --danger: #b91c1c;
  --radius-sm: 10px;
  --radius-md: 16px;
  --radius-lg: 22px;
  --shadow-card: 0 10px 30px rgb(15 23 42 / 7%);
}
```

变量名称可以调整，但必须做到全局统一。卡片、按钮、输入框、标签、顶部栏和页面外壳不再每个组件单独定义一套风格。

### 3.4 字体、间距和控件

- 中文优先使用 `PingFang SC`、`Microsoft YaHei`，英文和数字使用 `Inter` 或系统无衬线字体；
- 页面标题、区块标题、卡片标题形成明显层级；
- 基础间距以 4 或 8 为单位，避免组件之间出现不规律的空隙；
- 主按钮只有一个视觉重点；次按钮使用白底边框；危险按钮使用浅红背景或红色边框；
- 所有按钮在 hover、focus、disabled、loading 时都有明确反馈；
- 输入框获得焦点时有统一的蓝色外框；
- 状态标签统一为圆角胶囊，文字使用用户能看懂的中文。

## 4. 统一页面外壳和导航

### 4.1 客户页 `/`

顶部栏统一为：

- 左侧：品牌标识、`Mall AI 售后平台`、`可信电商售后 Agent`；
- 中间或左下：当前页面一句话说明，例如“订单事实、政策依据和售后方案在同一处完成”；
- 右侧：账号状态、我的售后、运营入口、人工处理入口；
- 移动端隐藏非必要文字链接，保留菜单或换行布局。

顶部栏下增加一条轻量产品说明带，不使用营销口号，建议展示：

`自然语言目标 → 事实与政策核验 → 方案确认 → 售后协同`

这条说明是视觉导航，不新增业务逻辑。

### 4.2 内部页面 `/operations`、`/service-operations`、`/quality`

三个页面使用同一套 `internal-page-shell`：

- 页面背景和容器宽度统一；
- 顶部左侧显示产品名和当前工作台名称；
- 顶部右侧统一显示 `返回客户咨询`；
- 页面标题下展示一句话说明和当前访问角色；
- 登录前的表单卡片、登录后的工作台、错误提示和加载状态统一；
- 不使用三个页面各自不同的边框、圆角和背景色。

可以保留 `operations-page-*`、`quality-page-*` 等现有类名，但最终视觉必须由公共变量控制。

## 5. 客户页一次性升级方案

### 5.1 页面结构

桌面端将客户页整理为三个区域：

1. 左侧：历史会话与账号相关入口；
2. 中间：当前对话、事实证据、政策依据和售后方案；
3. 右侧：开放任务 Agent 工作台。

建议结构：

```text
页面顶部
产品说明带
┌────────────┬─────────────────────────────┬──────────────────────┐
│ 历史会话   │ 对话与事实/政策/方案         │ Agent 任务工作台      │
│ 账号入口   │ 输入框与快捷目标             │ 目标、计划、证据、行动│
└────────────┴─────────────────────────────┴──────────────────────┘
```

当前 `AgentTaskWorkspace` 位于对话区上方，需要调整为右侧上下文面板或宽屏下的右栏。这样访客不用上下滚动，就能同时看到用户对话和 Agent 任务进展。

移动端按照以下顺序堆叠：

1. 页面头部；
2. 快速目标和开放任务；
3. 对话；
4. 事实、政策和方案卡；
5. 历史会话和人工协同记录。

### 5.2 客户页首屏重点

首屏必须优先出现以下内容：

- 产品定位；
- 一个可直接输入自然语言目标的入口；
- 当前 Agent 任务状态；
- 最近一条回答中的事实或行动卡；
- 明确的下一步按钮。

历史会话不能占据首屏主视觉。会话标题不再全部显示为“新的售后咨询”，应优先使用后端已有标题；没有标题时使用截断后的用户目标或“售后咨询 · 时间”。

### 5.3 对话和卡片层级

对话区不应只是消息气泡列表。每条 AI 回复按照以下层级展示：

1. AI 回复正文：说明当前结论；
2. `已核验事实`：订单、物流、库存等来源明确的事实；
3. `政策依据`：RAG 返回的政策来源和适用范围；
4. `判断与下一步`：问题分类、证据状态、允许的下一步；
5. `待确认方案`：需要用户确认后才提交的售后动作；
6. `已提交结果`：展示状态、时间和后续跟进。

每个卡片都要有清晰标题、状态标签和适当的视觉颜色。详细字段使用两列 `label / value`，长文本折叠或限制最大行宽。

### 5.4 人工协同记录

人工协同事项不应在客户页底部形成一串难以阅读的卡片。改为：

- 使用“人工协同”区块标题和事项数量；
- 每个事项显示原因、当前状态、客户需要补充的内容和最近一次进度；
- 时间线使用垂直节点样式；
- “查看进度”“补充信息”“重新开启”“取消事项”按主次排列；
- 只有危险操作使用红色，普通查看和补件不使用红色。

## 6. 开放任务 Agent 工作台升级方案

这是本次升级的核心展示区域，优先级高于装饰性视觉。

### 6.1 用户能看懂的内容

Agent 工作台要回答五个问题：

1. 用户让 Agent 完成什么目标？
2. Agent 现在处于哪个阶段？
3. Agent 已经确认了哪些事实？
4. 还缺什么，为什么需要用户补充？
5. 下一步会产生什么效果，是否需要确认？

不要直接把后端状态码、内部字段名和内部 ID 放到首屏。使用中文映射，例如：

| 后端状态 | 页面显示 |
| --- | --- |
| `created` | 已创建 |
| `planning` | 正在理解目标 |
| `executing` | 正在调查事实 |
| `replanning` | 正在根据新事实调整方案 |
| `waiting_for_user` | 等待你补充信息 |
| `waiting_for_async_task` | 等待业务查询完成 |
| `ready_to_commit` | 方案已准备，等待确认 |
| `committing` | 正在提交 |
| `completed` | 已完成 |
| `blocked` | 当前无法继续 |
| `failed` | 处理失败 |
| `cancelled` | 已取消 |

### 6.2 任务卡结构

每个任务卡统一为：

1. 任务标题：用户原始目标，最多两行；
2. 状态和计划版本：状态中文化，版本放在次级信息；
3. 进度条或步骤时间线：使用现有 `plan_nodes`；
4. 已获得的信息：使用现有 `artifacts`，区分“已核验”“推导”“方案”“不可用”；
5. 待解决问题：使用 `open_question`；
6. 结果或说明：使用 `outcome`、`execution_summary`；
7. 上下文摘要：将 `context_summary` 放入可展开的“处理摘要”，不要作为大段正文占据首屏；
8. 待确认行动：使用现有 `action`，主按钮为确认，次按钮为暂不提交；
9. 继续任务：仅在 `waiting_for_user` 时显示补充输入框；
10. 限制说明：将 `limitation_codes` 转成用户可读文案，作为底部提示。

### 6.3 任务时间线

`plan_nodes` 不再使用普通三列列表。改为垂直时间线或步骤卡：

- 已完成：绿色圆点和勾选；
- 进行中：蓝紫色圆点和轻量动画；
- 待处理：灰色圆点；
- 阻塞：琥珀色或红色圆点，并显示原因；
- 跳过：灰色文字和删除线或“未触发”。

时间线中只展示 `node_label` 和 `goal` 的用户可读内容，不展示内部工具名、数据库表名或原始请求参数。

### 6.4 行动卡

行动卡必须是页面最清晰的交互重点之一：

- 浅绿色或浅琥珀背景，表示这是方案而不是已经发生的写入；
- 标题说明预计效果；
- 正文说明原因和影响；
- 明确显示“确认后提交”或“暂不提交”；
- 确认后显示“已提交”“已撤回”“已阻塞”等结果状态；
- 不把 `action_skill` 直接显示给用户，可在“处理依据”折叠信息中显示“订单/物流/政策核验”。

## 7. 运营工作台 `/operations` 升级方案

### 7.1 首屏结构

登录后首屏顺序调整为：

1. 页面标题和当前账号状态；
2. 时间窗口、刷新、退出；
3. 关键指标卡片；
4. 转人工原因分布；
5. 人工跟进事项列表和右侧分析区。

### 7.2 指标卡片

从现有 `handoffOverview` 数据生成 3～4 张摘要卡：

- 去重后转人工总数；
- 当前统计窗口；
- 占比最高的转人工原因；
- 需要人工核实或证据不足的事项数（如果后端已有对应数据）。

不能编造后端不存在的数字。没有数据时显示“暂无数据”，不能显示 0 来伪造统计结果。

### 7.3 事项列表和分析

- 事项列表采用清晰的状态标签和原因标签；
- 当前选中事项使用明显但克制的蓝绿色边框；
- 右侧先展示最小化转接摘要，再显示“生成分析草稿”；
- 分析草稿分为“摘要、关注项、建议人工关注、边界、本次可信聚合”；
- 四类聚合数据使用小型统计卡，而不是连续文字；
- 分析正在生成时显示按钮 loading 和骨架占位，不能让页面看起来卡死。

## 8. 人工协同处理台 `/service-operations` 升级方案

这个页面服务于处理人员，重点是“快速领取、判断、补件、处理、结案”，不要做成客户页的复制版。

- 顶部显示处理人员身份、在线状态和刷新按钮；
- 左侧案件列表突出队列、状态、原因和创建时间；
- 右侧先显示案件状态和客户可见状态；
- 受控人工操作表单分组显示客户可见说明、内部备注、补件类型；
- 操作按钮根据状态显示，不能把不可用动作渲染成可点击；
- 状态推进采用小型步骤条：待领取 → 已领取 → 核验中 → 已处理 → 已结案；
- 错误提示和权限错误放在操作区附近，避免只在页面顶部出现。

## 9. 质量评测台 `/quality` 升级方案

### 9.1 首屏摘要

评测结果存在时，首屏先展示：

- 评测套件版本；
- 总 Case 数；
- 通过数；
- 失败数；
- 当前执行档位；
- 运行时间。

这些数字必须来自 `evaluation`，不允许前端计算出与后端不一致的“成功率”。如果需要显示通过率，使用后端总数和通过数计算，并处理总数为 0 的情况。

### 9.2 运行控制

运行控制区明确区分：

- `contract_mock`：确定性合同评测，默认、适合 CI；
- `live_model_synthetic`：合成数据上的手动模型评测；
- 失败归因建议：额外模型建议，必须人工审核。

显示“本次不会读取真实客户数据、不会执行订单写入”，但不要用大段免责声明压过主要操作。

### 9.3 Case 详情

评测 Case 默认以紧凑列表展示，每条包含：

- Case 编号和目标 Agent；
- 通过/失败状态；
- 预期结果；
- 实际安全投影；
- 违规代码（如有）；
- 工具轨迹摘要（如有）；
- 人工审批状态。

详细的合成轨迹、AI 归因建议和 RunManifest 使用 `<details>` 或展开面板，避免第一屏被长文本挤满。

### 9.4 质量支撑区

“版本化 Profile”“本地指标”“脱敏反馈候选”使用三张并列卡片，移动端纵向排列。每张卡片需要一个清晰标题、一句话解释和空状态。

## 10. 加载、空状态、错误和响应式要求

### 10.1 统一状态

所有页面统一使用：

- 加载：轻量骨架或“正在读取/生成”提示；
- 空状态：说明当前没有数据，并给出可执行的下一步；
- 错误：说明发生了什么和用户能做什么；
- 禁用：保留按钮位置，显示明确 disabled 状态；
- 成功：用绿色状态标签和一句结果说明，不弹出不可追踪的 alert。

### 10.2 响应式断点

至少验证以下宽度：

- 1440px：完整三栏客户工作台；
- 1280px：三栏仍可用，文字不重叠；
- 900px：内部工作台切换为两列或上下布局；
- 680px：客户页历史、聊天、Agent 工作台纵向堆叠；
- 390px：输入框、按钮、状态标签和长文本不溢出。

移动端必须保证：

- 操作按钮可点击区域足够大；
- 不出现横向滚动条；
- 表格或多列内容可以纵向阅读；
- 对话输入框固定在可见区域附近，但不能覆盖消息内容。

## 11. 可访问性和安全展示要求

- 所有表单输入都有 `label`；
- 所有按钮有明确文字或 `aria-label`；
- 键盘可以访问登录、发送、刷新、确认和取消操作；
- focus 状态清晰；
- 文本与背景对比度足够；
- 不能用颜色单独表示通过、失败、阻塞和待确认；
- 页面不输出原始 Token、密码、内部任务 ID、原始 Prompt、客户隐私和模型隐藏思考；
- 截图和 GIF 只使用合成数据。
