## Proposal and Collaboration Flow

`create_after_sales_draft` creates a server-held, revisioned ActionProposal.
An amendment generates revision N+1 and marks N superseded. Confirmation of N
returns a stale-proposal conflict; confirmation of the current revision causes
the Runtime to rebuild formal arguments and call Java only after revalidation.

`open_human_case` follows the same confirmation gate. Before confirmation it
has no Java side effect. The server then selects `commit_human_case`, validates
owner and current facts, and asks Java to create one minimal case projection.
Duplicate confirmation is idempotent and a cross-account attempt returns 404.

## Public API and UI

`POST /api/agent-tasks`, task continuation, action amendment and confirmation
are exposed through safe DTOs. The customer workspace shows a proposal revision
and stale-conflict state; it never receives internal task IDs, raw tool payloads,
credentials, RAG source text, Prompt or reasoning. The operations workspace
shows only minimal Java-provided case projections.
