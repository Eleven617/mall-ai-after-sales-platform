学习原则：当前版按已核实代码讲；下一版按设计讲；实现AI完成后再做设计与代码对照验收。不把讲过当掌握、不反复背术语、不等待功能实现才学习设计。

## 1. 必须先纠正的认识

当前并非只有旧诊断能登记人工。统一会话入口可以进入TaskRuntime；open_human_case产生提案，确认后commit_human_case调用登记接口。Java已有人工案件、领取、补件、核验、处理和结案能力。

旧诊断外层检查verified_facts，TaskRuntime使用自己的Artifact和提案校验。两者不能混讲。运营当前读取的是粗粒度交接记录，并不能据此完整解释客户为何要求人工。

## 2. 每节固定讲法

先说明客户正在做什么和本节要回答的问题，再解释已有代码怎样处理；接着说明下一版改变哪一处、谁负责、输入输出、存储、失败与恢复。每次只推进一节，使用一个合成案例。术语首次出现先讲对象和作用，再说英文或类名。

每节末给一条标准面试回答与一条基于已学内容的追问。用户要求直接讲时不强行答题。关联架构以解释必要边界为准，不每次重复全套Vue/FastAPI/Java/MySQL。

## 4. 第一节讲义：客户说“转人工”以后到底发生什么

合成案例：客户只问换货政策，没有订单号，之后说“我没听明白，帮我转人工”。

当前：Vue统一入口的提示词允许把明确转人工交给任务路径；任务可形成open_human_case提案。确认后commit_human_case还要满足当前Artifact/原因/分类契约，再调用Java。不能只看到入口提示词就保证本案例已全链路成功。原有政策RAG分支没有自动调用旧诊断人工登记。

下一版：自然语言识别或常驻按钮形成交接卡；即使缺订单事实也能生成一般咨询的受控上下文。客户确认后，Java创建人工案件，显示排队状态；模型分类可以随后完成。这里没有创建退货/换货申请，因为客户此刻请求的是人工解释。

四个不同状态：提出请求（客户表达）→确认交接（针对当前卡）→已建案（Java提交）→人工领取（处理人员动作）。系统建议未接受停在建议状态；不能在统计里算成实际交接。

职责：Python组织交接材料和模型分析；Java判身份/归属/幂等/队列与案件状态；人工处理人员解决客户事项；运营分析人员看原因与趋势。模型不能根据一句不满自行断言技术故障。

实现区别：旧路径主要判断“诊断结果是否符合登记条件”；新版首先承认“客户请求人工”本身是独立业务意愿，再按安全契约建立案件，背景不足通过人工补件解决，不用先完成自动诊断来获得人工资格。

标准面试回答：现有系统已具备人工案件与可靠写入，但交接材料主要是诊断标签，客户主动请求的体验和运营原因分析仍不足。下一版统一各入口到版本化交接提案和Java案件服务，补充脱敏任务上下文、区分客户陈述与系统事实，异步分类并由人工修正；运营采用同一统计口径追踪重复问题，改进结论必须有证据。

追问与参考：客户无订单号是否拒绝转人工？不应一概拒绝。政策解释可创建咨询案件；需要操作具体订单时，后续再核验订单归属和资格。人工服务权限与退款写入权限不是同一件事。
