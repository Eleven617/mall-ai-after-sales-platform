# 第一阶段重写对接说明：安全上下文摘要与相似问题发现

日期：2026-10-12。状态：已对齐的需求修订，待另一个实现 Agent 核对源码并重写第一阶段设计。

配套原文件：`docs/HUMAN_HANDOFF_SEMANTIC_PHASE1_REQUIREMENTS_20261011.md`。

本说明修正原文件中“第一阶段不要求单条摘要模型调用”的决定。就本次需求而言，冲突处以本说明为准；其余身份、Java 权威、确认、幂等、权限和生命周期约束继续适用。不要将本文描述的目标表述成当前已实现。

## 1. 用户真正要解决的问题

运营需要知道客户想解决什么、系统已经做了什么、具体哪里没有解决，以及哪些问题反复出现。只有“换货、聊天入口、主动转人工”等枚举，无法满足这个目标。

第一阶段必须具备：相关安全上下文 → 大模型结构化问题摘要 → 本地 Embedding 相似候选 → 运营人工归组 → 有证据的组分析草案与改进项。

固定字段负责可靠筛选和统计；摘要负责表达具体问题。不能只增加一个字符串字段，再用固定句“客户请求人工”填满，就称作摘要功能。

## 2. 重写范围

保留原设计中的明确人工请求、按钮、接受系统建议三类入口，保留 Runtime 提案确认和 Java 最终创建案件。

必须修改原设计的范围、流程图、问题数据来源、数据实体、worker、模型预算、接口、页面状态、保留删除、实施顺序和验收章节。不能只在末尾附一段“也可以用模型”，留下正文互相矛盾。

第二阶段继续保留自动聚类、算法对照与趋势验证；将原第二阶段中的单条上下文摘要提升到第一阶段。阶段二仍可研究更好的摘要模型和质量优化，但不能继续将核心摘要能力整体后移。

## 3. 各组件到底做什么

| 组件 | 输入 | 输出/职责 |
| --- | --- | --- |
| 意图识别模型 | 当前消息与既有允许上下文 | 选择 `handoff` 等路由，不创建案件 |
| Python 交接准备逻辑 | 入口、身份、关联任务 | 确认当前问题、准备提案与安全上下文快照 |
| 安全上下文构造器 | 已批准的当前问题投影 | 筛选、脱敏、区分来源、限制长度；无模型业务写入 |
| Java Portal | 客户确认、提案版本/hash、安全输入快照 | 校验并创建案件；同事务保存相关记录、审计、分析任务和 Outbox |
| 单条摘要模型 | Java 授权领取的冻结安全快照 | 目标、处理过程、未解决问题、客户陈述及来源引用 |
| Python 输出校验 | 模型结构化结果 | Schema、敏感信息、来源白名单、矛盾检查；不合格不发布 |
| Java 分析任务服务 | 有效租约与输入版本对应的结果 | 保存模型派生摘要版本，维护状态与审计 |
| 本地 Embedding | 有效摘要中的目标与未解决问题 | 向量；供相似查询使用 |
| 运营人员 | 摘要、事实标记、统计、相似候选 | 判断同问题、归组、复核草案与推动改进 |
| 组分析模型 | 人工组、Java 统计、有限安全样例 | 有引用的共性、待验证假设与改进建议 |

模型生成分析产物，不取得业务写权限。案件/任务状态由服务端协议推进；模型不能返回可直接执行的状态变更命令。

## 4. 固定时序：案件创建与摘要解耦

1. 客户要求人工或点击按钮，统一入口进入准备流程。信息询问不能误判成动作请求。
2. Python 确定当前问题及归属，构造安全上下文快照。客户看到关联问题与交接说明，可选补充/纠正简短描述；不强制客户重述聊天。
3. 快照引用、版本/hash 受提案约束。准备阶段只使用允许的短期存储和 TTL；没有确认，不进入运营持久记录或后台摘要队列。
4. 客户明确确认后，Java 校验并保存案件、基础运营字段、安全输入快照、摘要任务、审计和相关 Outbox。此处选择同事务创建摘要任务；事件不得再无标识创建另一份任务。
5. Java 提交成功即返回案件结果。客户不等待摘要、Embedding 或组分析。
6. Python worker 通过 Java 内部 API 领取摘要任务与允许的快照。调用单条摘要模型，验证输出，按租约和输入版本回报 Java。
7. 摘要有效后进入本地向量生成；Java 登记派生版本和索引任务。运营页面分别显示摘要状态与向量状态。
8. 运营查看具体问题，找相似案例、人工归组，再按需生成组分析草案。

选择单一路径：第一阶段默认全部在确认后异步摘要，不再同时实现“确认前等一次、超时后再摘要一次”的双路径。

客户确认的是交接动作和当时冻结的输入；异步生成摘要标注“AI 生成，未人工复核”，不能写成“客户确认的总结”。修订摘要只改变派生版本，不能修改原确认内容或重新触发案件创建。

## 5. 模型能读到什么上下文

目标是保留问题语义，而不是复制历史聊天。实现 Agent 只能读取源码及合成/脱敏样本，不读取真实原始客户对话。

输入来源优先级：

1. 已有且经过 allow-list 审查的当前任务目标、有效 Artifact 投影、服务端执行结果类别和事实引用。
2. 已存在且允许使用的脱敏会话片段：保留说话角色、先后顺序、同一问题范围与必要语义。
3. 客户在当前交接中可选提供并经处理的简短描述。

必须先核对项目是否具备第 2 项。若没有，重写设计应明确这是缺失的数据生产能力、需要新增什么安全投影合同。不得写成“直接读取历史聊天再总结”，不得用本需求擅自放开根 AGENTS.md 对原始对话的约束。需要扩大原始数据处理范围时，应单独列明具体变更供用户决策；已有允许数据的设计工作照常完成。

选取当前问题相关的连续安全片段，优先明确目标、最近未解决追问和失败/完成结果。初始建议最多 8 条片段、3000 中文字符、总输入 4000 tokens；按真实 tokenizer 控制上限，超限记录截断及缺失信息。不能只有“最后一句转人工”，也不能混入其他任务或客户的数据。

每条片段携带内部 opaque 来源引用和类型：customer_statement、assistant_explanation、verified_business_fact、execution_result。助手曾说过的话不能自动升级成已核验业务事实。

允许事实使用受控投影；完整工具载荷、订单号、地址、手机号、Token、RAG 原文不进入新增模型请求。

## 6. 如何清洗，如何防止摘要编造

模型调用前：先字段白名单，再敏感字段排除，随后对允许短文本做格式规则与个人信息检测、遮蔽、长度控制。单纯正则不足以保证完全安全；安全性不确定的片段不得发送，保留缺失标记。不得先把原文发给外部模型让它脱敏。

调用时：输入片段视为数据；模型不接受片段中的指令，无工具和数据库权限，输出严格 Schema。明确禁止把未知补全成事实、把要求人工等同于不满意、把客户陈述等同于核验结果。

输出后：校验结构、长度、敏感信息、引用白名单及受控事实一致性。引用有效只能证明来源存在，不能完全证明自然语言忠实；通过专用摘要评测和人工纠正补足，不能宣传 Schema 可以消除幻觉。

## 7. 摘要输出合同

| 字段 | 内容 | 缺失处理 |
| --- | --- | --- |
| customer_goal | 客户希望完成什么，附来源引用 | null |
| handling_steps | 已回答/查询/尝试事项，每条含结果类别和来源 | [] |
| unresolved_question | 当前具体未解决的问题，附来源 | null |
| customer_statements | 对理解问题必要的客户陈述，明确未核验 | [] |
| handoff_reason_statement | 客户明确说出的转人工原因 | null；不能猜测 |
| uncertainty_notes | 缺失、截断、歧义和证据不足 | [] |
| evidence_refs | 输入允许的来源引用 | [] |

主题、来源、渠道、客户选择原因、业务状态、已核验事实、时间等权威字段由程序/Java 提供，模型不能覆盖。模型建议的主题如需提供，应另设 suggested_topic，不直接改官方分类。

Java 保存 input_snapshot_hash、输入/脱敏/Prompt/Schema/模型版本、summary_version、生成时间、复核状态与安全错误码。运营公开 DTO 不包含内部 Prompt、完整片段输入、原始对话或 lease token。

## 8. 一组必须通过的合成例子

安全输入：客户询问换货凭证；助手解释需要材料；客户追问“没有开箱视频还能申请吗”；系统未给出有依据的答案；客户要求人工。

期望摘要：目标“确认缺少开箱视频时能否申请换货”；过程“已解释一般材料要求”；未解决问题“缺少该视频是否影响申请尚未明确”。

禁止输出：“客户换货资格不通过”“系统已拒绝换货”“客户因不满转人工”。输入没有这些证据。

与另一个“没有开箱录像可否换货”的安全案例，应能产生可检验的相似候选；“换货寄到哪里”应作为同主题不同问题的难负例。摘要质量必须先验收，再评估 Embedding，避免向量只聚合模板措辞。

## 9. 持久化、恢复与失败

Java 保存安全输入快照，便于 worker 重启后重新领取，不依赖进程内临时聊天。若安全快照不足，案件照常创建，摘要状态标记 INSUFFICIENT_CONTEXT；不能后台偷偷回查原聊天。

摘要状态：PENDING、RUNNING、SUCCEEDED、INSUFFICIENT_CONTEXT、FAILED、DELETED；索引状态单独维护，摘要成功不等于向量已就绪。

初始保护参数建议：并发 1、单次模型超时 30 秒、输出上限 1000 tokens、每个输入版本最多 2 次模型尝试（含结构纠正），租约 90 秒。记录真实使用量与延迟，不声称是实测 SLA；预算用尽后保留可见失败状态和授权人工重试入口。

幂等任务标识包含 case_ref、input_snapshot_hash、Prompt/Schema/模型版本；结果提交校验租约与输入版本。进程崩溃可能导致模型请求重复计费，需要预算和请求记录约束；不能承诺外部模型精确一次。

Java 超时按原请求标识查询/对账，不能换标识重建案件。摘要失败不取消案件；旧版本结果不能覆盖新版本或复活已删除记录。

人工修改摘要必须留审计、来源与新版本，旧向量失效并重建；组分析引用过期摘要时标记需更新。输入、摘要、向量、含内容的组草案都继承源记录的保留/删除约束。查询先过滤失效记录，后台幂等清理派生索引。

## 10. 运营最终看到什么

列表：主题、来源、时间、摘要状态、具体未解决问题短句。详情：客户目标、已处理过程、未解决问题、客户陈述/核验事实区分、数据缺口、AI/人工复核标识。

摘要待生成时显示真实状态，不能用“客户请求人工”冒充已生成内容。失败或内容不足时仍能筛选和统计基础字段。

相似查询用有效摘要的目标与未解决问题构造版本化向量输入；不把所有过程和通用“转人工”句塞进去。保留原方案的精确余弦基线、阈值校准、权限过滤、同版本比较和人工归组。

组分析另一次按需模型调用：读取人工确认的有限样例和 Java 统计，输出共性、证据、假设、验证建议。不能把单条摘要与跨案例分析混称为同一功能。

## 11. 新模型与可见性变更登记

- 用户可见性：客户快速得到交接结果；运营随后看到具体问题摘要及生成/复核状态。
- 数据范围：新增模型仅接收批准的安全快照；不自动扩大原始会话读取范围；模型提供方数据保留规则需核对。
- 成本与延迟：单条异步摘要新增调用；按案件与输入版本控制次数、并发、token 与预算，不能无上限每轮聊天总结。
- 非目标：自动定责、自动业务执行、自动合组、自动分析所有聊天。
- 失败回退：普通交接继续可用，记录失败/内容不足；保留基础字段，不伪造摘要。
- 实际验收：先合成确定性合同，再单独记录获授权的 live 摘要质量与本地端到端验证。未执行必须明示。

## 12. 重写与实施验收要求

重写后的文档必须回答每一步：输入从哪来、谁处理、保存在哪、什么时候发生、失败如何处理、谁能看到、凭什么证明正确。

至少覆盖：明确请求与政策询问区别；多任务归属；无订单一般咨询；未确认不建案/不进分析；确认重试不重复；安全快照来源不足；隐私与提示注入；保留否定和未解决追问；客户陈述不升级成事实；过期事实不用于当前判断；截断提示；worker 重启；删除竞态；模型结构失败和总预算；人工纠正导致向量失效。

模型质量用独立合成样本人工评估：目标准确性、未解决问题保留率、已处理过程忠实性、无依据新增事实、敏感信息泄漏及摘要覆盖率。每项报告样本数与失败例；不能只用 Schema 通过率宣称摘要正确。

首批验收门槛：确定性安全、权限、版本和幂等合同全部通过；质量评测中发现无依据业务事实或敏感泄漏应阻断该模型配置发布并修正复验。零个已发现错误不等于生产风险为零。其余质量阈值应在标注规范和样本规模明确后冻结，不能看完保留集再降低标准。

实现必须遵守仓库 AGENTS.md 的测试、迁移与发布门禁，分别记录确定性、现场、live model 证据。本文只授权需求对接文档，不代替实现任务中对模型运行或部署的授权。

## 13. 可直接发给另一个 Agent 的任务说明

请先读取本文件、原第一阶段设计及根 AGENTS.md，核对现有交接和安全上下文相关源码，重写第一阶段设计。核心修正：把“模型从批准的相关安全上下文生成结构化问题摘要”纳入第一阶段必需能力。客户确认后 Java 先保存案件与安全输入快照，异步摘要，再生成 Embedding；运营看到具体目标、处理过程和未解决问题，进行相似检索与人工归组。

先输出可实施的修订版文档及旧决策替换清单，不直接修改业务实现。核实每个输入字段是否真实存在，不把教学示例当作源码；缺少脱敏会话投影时明确数据合同缺口，不擅自读取原始客户聊天或放宽权限。统一更新第一阶段所有受影响章节，并修正第二阶段中重复后移的摘要范围。保留已有身份、确认、幂等、Java 事务、角色隔离及删除约束。

交付说明须列出：代码已具备什么、拟新增什么、哪些输入仍不可得、哪些具体设计决定仍需要用户决策。不能将模板枚举统计作为完整问题分析交付，也不能将新设计宣称已实现。
